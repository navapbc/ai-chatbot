# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `ai-chatbot` Next.js application. In the Labs ASP project it is consumed as a Git submodule (tracking the `develop` branch), but it also lives standalone at [navapbc/ai-chatbot](https://github.com/navapbc/ai-chatbot) — keep changes here self-contained to the app.

## Commands

```bash
pnpm dev              # next dev --turbo
pnpm eve:dev          # dotenv -e .env.local -- eve dev — local Eve agent server (see Eve agent below)
pnpm build            # runs lib/db/migrate THEN next build
pnpm lint             # biome lint --write --unsafe
pnpm format           # biome format --write
pnpm test             # vitest (browser mode, chromium via Playwright)
pnpm test:playwright  # Playwright e2e tests (sets PLAYWRIGHT=True)

# Database (Drizzle)
pnpm db:generate      # generate migrations from schema
pnpm db:migrate       # apply migrations (npx tsx lib/db/migrate.ts)
pnpm db:studio        # open Drizzle Studio (read-only browsing)
pnpm db:push          # push schema without migration files
pnpm db:check         # check migration consistency

# Braintrust evals (evals/*.eval.ts — see Evals & observability below)
pnpm eval                  # run every evals/*.eval.ts locally (needs .env.local)
pnpm eval:ci                # same, without dotenv (CI already has the env)
pnpm eval:tool-selection    # run a single eval file
pnpm eval:check-harness     # sanity-check the browser eval harness itself
pnpm eval:online:apply      # apply online scoring rules to a live Braintrust project
```

`.github/workflows/evals.yml` (PR-triggered) gates every matrix leg on its provider API key being present as a secret and skips the leg (green, not passing) when it isn't — a green Evals check does not by itself mean the evals ran; check the job logs for `::warning::...skipping` before trusting it.

Run a single unit test: `pnpm exec vitest run <path>` (e.g. `pnpm exec vitest run tests/client/some.test.tsx`).

Node-only tests under `tests/agent/**` (anything touching `node:fs`, `eve/*` tools, etc.) are excluded from the default browser-mode `pnpm test` because importing them crashes the browser runner — run them explicitly with `pnpm exec vitest run --config vitest.config.node.mjs`.

Always use `pnpm` (packageManager is pinned). Ask before installing any new dependency.

## Stack

Next.js 16 (App Router) · React 19 · Vercel AI SDK v7 (`ai` package) · Zod v4 · [Eve](https://eve.dev/docs) (durable agent runtime, mounted via `withEve()`) · Drizzle ORM + Postgres · next-auth v5 (beta, with guest auth) · Biome (lint/format, 2-space indent, 80-col) · Tailwind · TypeScript path alias `@/*` → repo root.

## Architecture

**Two agent implementations, both live in this repo.** Production chat traffic is served by the legacy `streamText` loop in `app/(chat)/api/chat/route.ts` — the `useEveAgent` feature flag that would route a chat through the Eve agent instead defaults to `false` (`lib/feature-flags.ts`). But the Eve *runtime* itself is not a side experiment: `next.config.ts` wraps the app in `withEve()`, and in deployment (`scripts/start-container.sh`, `terraform/cloud_run.tf`) Eve runs as a sibling process inside the same Cloud Run container with its durable session state backed by Postgres. The practical consequence: agent behavior (prompts, tools, compaction) is currently **duplicated across two trees** — `lib/ai/prompts/` + `lib/ai/tools/` for the legacy route, `agent/instructions.md` + `agent/skills/` + `agent/tools/` for Eve — and a change to "how the agent behaves" needs to either target the right one or update both. Don't trust `agent/README.md`'s framing of itself as a "demonstrative conversion" that doesn't replace production — that predates the Cloud Run/Postgres wiring in `agent/agent.ts` and is stale.

**Routes** — `app/` uses App Router route groups: `(auth)` (login/register/next-auth handlers), `(chat)` (main chat UI + APIs), `(landing)`. API routes live under `app/(chat)/api/` (`chat` — legacy agent loop, `eve-chat` — Eve adapter route, `document`, `files`, `history`, `suggestions`, `vote`, `participants` (POST with a JSON `{q}` body; summaries only; there is no GET, so a name never reaches a URL), and under `relay/`: `token` (extension token only, user-bound), `classify-field`, `config`, `runs/[runId]` (GET run state) and `runs/[runId]/stop` (POST) and `agent-token` — internal; see Extension runs below). `app/api/kernel-browser` sits outside the `(chat)` group and serves the live browser-view URL to the UI regardless of which transport produced it (see Browser automation below).

**Agent loop (legacy, default path)** — `app/(chat)/api/chat/route.ts` runs `streamText` as a multi-step agent (`stopWhen: [stepCountIs(500), abort]`) with `prepareStep` switching the model mid-run. `maxDuration = 300` (5 min) for long web-automation tasks. Resumable streaming is wired via `resumable-stream` + Redis. In-flight chats can be cancelled through `lib/chat-abort-registry.ts` (the `/api/chat/stop` route). Context is trimmed by `lib/ai/context-compression.ts`.

**Eve agent (opt-in path)** — `agent/` defines a second, parallel agent via Eve: `agent.ts` (top-level `defineAgent`), `instructions.md` + `instructions/date.ts` (always-on instructions), `skills/browser-automation`, `skills/benefits-application` and `skills/extension-run` (situational reference material, loaded on demand — the Eve equivalent of the legacy `readReference` tool; `extension-run` applies only to relay runs), `tools/` (real implementations, not stubs: `browser`, `check_submit_gate`, `action_label`, `form_summary`, `gap_analysis`, `resolve_field_value`, `report_progress`, plus a `defineState`-based `update_working_memory` prototype), and `subagents/requirements_research` + `subagents/form_review` (each carries its own copies of instructions/tools: a declared Eve subagent inherits the session's auth, so relay attributes reach its tools, but not the parent's tools, skills or state). `app/(chat)/api/eve-chat/route.ts` is the adapter: it creates/continues an Eve session, translates Eve's NDJSON event stream into AI SDK SSE (`lib/ai/eve/stream-adapter.ts`, `eve-client.ts`), and tracks per-chat session continuity in Postgres (`lib/ai/eve/run-store.ts`, the `EveRun` table; follow-up turns claim the continuation token with a compare-and-set so turns arriving together cannot both reach Eve; the claim is released when continue returns, so a follow-up sent while Eve is still running a turn can reach Eve, which folds it into the next turn). Models are called directly against Vertex AI rather than through the AI SDK Gateway, defaulting to `claude-opus-5` — a different default than the legacy route's `claude-opus-4-7` (`agent/agent.ts`); compaction uses Eve's built-in `thresholdPercent` (no `prepareStep`-equivalent hook exists, so this does not use `lib/ai/context-compression.ts`). Eve's durable workflow state uses `@workflow/world-postgres` when `WORKFLOW_POSTGRES_URL` is set (deployment), falling back to Eve's local file world otherwise (local dev) — see the extensive comments in `agent/agent.ts` before touching this, the package is pinned to a specific version for World-spec-compatibility reasons.

**Extension runs (relay)** — off unless `RELAY_RUNS_ENABLED` is exactly `1` (set nowhere in deployment yet). A first `eve-chat` turn with `relay: { origin, participant, model? }` and no client message creates a relay run (`lib/relay/run-input.ts` validates it and builds the opening message on the server; guests are refused by `lib/relay/route-guard.ts`, `model` must be in `RELAY_ALLOWED_MODELS`, and each user is capped at `RELAY_MAX_RUNS_PER_HOUR`, default 20, a soft check-then-create cap): the chat id is the run id, a partial unique index keeps one relay `EveRun` per chat id, another user's existing relay run for that id is refused before any Eve session exists, the `EveRun` row stores the origin, and the Eve session gets only a non-secret run reference (`x-eve-relay-run`, `x-eve-relay-url`, granted by `agent/channels/eve.ts` on loopback with `EVE_INTERNAL_SECRET`; relay headers without that grant are rejected with a 403). Eve persists session attributes, so no relay token is ever put there: the `browser` tool fetches a short-lived agent token at call time (`lib/relay/agent-token.ts`) from the internal `app/(chat)/api/relay/agent-token/route.ts`, which mints only for the Eve session stored on the run and answers every refusal with a bodyless 404. The public `relay/token` route mints only the extension token for the signed-in user, reading the origin from the stored run; tokens carry `sub` and the hub refuses an extension/agent pair whose `sub` differs. `EVE_INTERNAL_SECRET` shorter than 32 characters is treated as unset (`lib/relay/internal-secret.ts`). On relay runs the adapter hides tool inputs in the client stream (`lib/relay/tool-input.ts`). Eve reaches Next at `APP_INTERNAL_URL` (set by `scripts/start-container.sh`, default `http://127.0.0.1:3000`). Relay runs get structured `ask_question` cards with server-validated answers and `report_progress` status, both persisted on the run row. Auth: the extension calls the app with `credentials: 'include'` (`extension/src/app-api.ts`); a Lax session cookie reaches the app from the worker once `host_permissions` covers the build-time `APP_ORIGIN` (exact https origin, so it must equal the deployed origin; GET carries no `Origin`, POST carries `chrome-extension://<id>`). `RELAY_EXTENSION_ORIGIN` (full `chrome-extension://<id>`; unset means no check) makes every relay and participant route refuse a present, different `Origin` and require it on state-changing routes (`lib/relay/request-origin.ts`, `route-guard.ts`). Ended runs: `EveRun.endedAt` is set by `POST relay/runs/[runId]/stop` (the panel's Stop calls it, then the worker `stopRun`), which ends the row, then cancels the Eve turn (every call tries the cancel, a failure does not undo the end). An ended run never mints a token (bodyless 404) and `eve-chat` answers it with `run_ended` (400); there is no resume. `GET relay/runs/[runId]` returns origin, progress, `pending` (`[]` once ended), `endedAt` and `phase` (`ended`, `needs_you` when questions are pending, `review` when the turn is idle, else `working`). On relay runs `eve-chat` keeps reading Eve's stream and persisting pending questions, cursor and token after the client disconnects (a throwing client write is swallowed), and closes the Eve body at the end; web chats are unchanged. On a relay first turn, right after `store.create`, a request signal that has already aborted ends the row, cancels the Eve turn and answers 499 (the panel timed out or closed while the session create ran; Next 16 abort propagation is unverified, so the panel's open-time sweep is the backstop). The Eve `browser` tool (`lib/relay/eve-relay-browser.ts`) also treats `extension did not answer` (the first command, sent before the extension registered) as a lost connection, so a retry-safe command is rotated and retried; and when the worker holds the run for an origin change it waits out the hold, polling `get url` every 3 s for about 125 s, then re-runs a retry-safe command or reports `CONNECTION_RESTORED` for any other; it never replays a non-retry-safe command. There is no hub queue for commands while the extension state is `unknown`, so that first command can stall up to 30 s before the retry. Relay transport and logs (`relay/server.ts`, `relay/hub.ts`): the extension token travels as the WebSocket subprotocol on `/extension`, offered as `relay.v1, <token>`; the relay selects the fixed value `relay.v1` and never echoes the token (Chrome fails a handshake that selects none), and the query token on `/extension` remains only as a transition fallback for old clients. `/cdp` (the agent leg) is query-only because agent-browser takes a plain `ws://` URL. A closed run leaves an in-memory tombstone in the hub for the token TTL, so a token cannot re-register it in that window (in memory only, after terminal closes only; a relay restart clears it). Relay log lines carry `severity` (Cloud Logging reads it), the accepted line carries the run's `origin` (never a URL, header, token or `sub`), and socket errors are logged by `code` only, at most 10 per 60 s process-wide (the dropped count is reported on the next logged error). Each peer's outbound queue is capped at 64 MiB (2x the 32 MiB inbound ceiling, `MAX_BUFFERED_BYTES`); past it the run closes with `send buffer full`. The `command` log line is flat `{event:'command', durationMs}` and feeds the log-based metric. What a relay restart or the one-hour socket limit does to a live run is unverified: the worker reconnects with the same token, the Eve tool rotates and retries, and the panel shows no reconnecting state. Pilot rollout steps, the Chrome policy templates and the checks on a managed Chrome are in `docs/rollout-pilot.md`.

**Models / providers** — `lib/ai/providers.ts`. Web automation uses `webAutomationModel = vertexAnthropic('claude-opus-4-7')` via Google Vertex AI; `prepareStepModel` uses `claude-haiku-4-5`. Both the legacy route and the Eve agent require `GOOGLE_VERTEX_LOCATION=global` — the opus models have no quota on any regional Vertex endpoint on this project, only `global`; a 429 there almost always means this env var, not a real quota exhaustion. A `customProvider` exposes selectable dev-only models (GPT and Claude variants, hidden in production; the dev model picker can also drive the Eve agent's model per-session via `lib/ai/eve/model-map.ts`). In test env, models are swapped for mocks from `lib/ai/models.test.ts` — **that file is not a test**; it exports mocks and is excluded from the vitest run.

**Tools** — `lib/ai/tools/` (legacy route). Tools are factory functions bound to a session/user where needed (e.g. `createBrowserTool(sessionId, userId)`, `createCheckSubmitGateTool`) or to the participant record (`createGapAnalysisTool`, `createFormSummaryTool`, `createResolveFieldValueTool` — see Jev below). Wired into the agent in the chat route: `browser`, `gap-analysis`, `form-summary`, `resolve-field-value`, `check-submit-gate`, `action-label`, `read-reference`, plus document/suggestion tools. The Eve agent's equivalents live under `agent/tools/` (see above) and are separate implementations, not shared code.

**Browser automation (Kernel.sh)** — `lib/kernel/browser.ts` creates and owns remote browser sessions on Kernel.sh via `@onkernel/sdk` (profiles, replay recording, standby) for the legacy route; `lib/kernel/eve-browser.ts` is a separate, minimal reimplementation for the Eve agent (Eve's bundler cannot import anything that transitively pulls in `server-only`, which `browser.ts` does via `lib/db/queries.ts` — known duplication debt, not yet consolidated). `agent-browser` is a **native Rust CLI**, not a library: `lib/kernel/cli.ts` runs it as a subprocess and attaches it to the Kernel browser with `--cdp <cdp_ws_url>`, keeping session lifecycle on our side. Its daemon is keyed by `--session` (see `cliSessionName`) and holds the CDP connection between calls, so `@eN` refs survive across commands. Sessions live in an **in-memory cache** keyed `${userId}:${sessionId}` — this assumes a single server instance; Kernel.sh owns lifecycle/timeout. `lib/kernel/session-store.ts` holds pure, dependency-free helpers factored out so session-status logic can be unit-tested without pulling in `@onkernel/sdk`. `lib/kernel/telemetry.ts` bridges Kernel's own browser telemetry (console errors, CDP connect/disconnect, captcha results, OOM kills) into OpenTelemetry spans; the `network` category is deliberately left off because request data can contain applicant PII. The `browser` tool (`lib/ai/tools/browser.ts`) serializes commands per session via a mutex queue so a snapshot's refs still describe the page when the next command runs. The agent emits the CLI's own argv (`["snapshot", "-i"]`, `["click", "@e1"]`) rather than a translated action vocabulary, so new agent-browser commands work on upgrade; `snapshot` first is the expected discipline. Session IDs are `${chatId}-${userId}`. Because the Eve agent runs in a separate process from Next, its browser's live-view URL can't be read back out of `lib/kernel/browser.ts`'s in-memory map — `lib/kernel/live-view-store.ts` is a second in-memory store the `eve-chat` route writes into and `app/api/kernel-browser` reads from, so the live browser-view UI works the same regardless of which transport is driving.

**Participant data** — participants for the extension come from a `Participant` table in the app's Postgres database (the one `DATABASE_URL` points to) through `lib/data/participant-source.ts`; the API returns summaries only and the full record stays on the server (seed with `scripts/seed-participants.ts`). For the web chat, `lib/data/participants.ts` holds the seed records and `buildApplicationPrompt` turns one into a chat message, so the agent receives the participant JSON inline in the caseworker's first message (an earlier Apricot integration was fully removed). Both the suggested-action buttons (`components/suggested-actions.tsx`) and the landing page Client ID lookup (`components/benefit-applications-landing.tsx`) go through that helper.

**Sensitive-value redaction (relay runs)** — what the model may see of a caseworker's tab. Nothing here needs a flag except trace scrubbing. The extension worker redacts every reply and event before it goes up the relay (`extension/src/redaction.ts` wraps `lib/relay/redactor.ts`); both are free of `server-only` so the Eve bundle and the extension build can import them. `lib/relay/sensitive-fields.ts` is the pure classifier (label, name, id, autocomplete, placeholder; a value-shaped placeholder counts) that decides a field is sensitive: its value, name and attributes are masked as `[masked]` in accessibility trees, `DOM.describeNode` and URLs, and a describe failure with no other signal fails closed. Values registered through the worker's `addKnownValue` message are scrubbed from everything in every encoded form (the side panel is the caller and binds both messages to the run id; it registers values only through `typeSensitive` (below), so after `startRun` it sends `registrationComplete(runId, 0)`; they live in worker memory, are carried across a same-run token refresh (in memory, cleared on every other end) and are lost on a worker restart, after which the run starts `needsRegistration` and the bridge refuses every CDP command that can return page text until the panel sends `registrationComplete`, count may be 0; `getRunStatus` reports the flag. A `startRun` for a run id this worker already began, with no live run of that id, also starts `needsRegistration`: the worker keeps the 20 most recent begun run ids, ids only, in `chrome.storage.session`). The redactor takes a `classifyExtra` hook: the worker's Jev classifier (`extension/src/jev-classifier.ts`, via `classify-field`) can only add masking (OR with the deterministic verdict). The route answers `true`, `false` or `null` per field; `null` means no verdict (Jev disabled, failing, timing out or answering malformed), and the classifier rejects on it, as on any request failure, so the redactor caches nothing and keeps the deterministic verdict. `Redactor.masksFilledField` gives the verdict the redactor would give a field once it holds a value (accessibility node, `describe`, `classifyExtra`) and answers `false` on any failure or unknown, so not knowing means not typing. It exposes a failure count. Jev disabled is a supported configuration: `JEV_FEATURES` must include `sensitive-field` only to get Jev's extra masking. A tab that leaves the run's origin for another https origin holds the run for 60 s (120 s cap) rather than ending it, refusing every command and forwarding no events, until the tab returns, the worker message `allowOrigin` adds the origin for this run (max 3), or the hold expires (`left-origin`); other schemes end the run at once. The hub still binds `Page.navigate` to the token origin. A shape guard also masks SSN-like and 9+ digit runs in `Runtime.*` results and URL query/path. `lib/relay/screenshot-mask.ts` masks sensitive fields in pixels around `Page.captureScreenshot` (per-tab lock, isolated worlds) and refuses the screenshot when it cannot, or when a registered value is in page text. `lib/relay/frames.ts` scopes same-site cross-origin iframes (they share the tab session): handles, contexts and events of a frame outside `allowedFrameOrigins` are refused or dropped, and a screenshot is refused while one is present. `lib/relay/policy.ts` also holds the event allowlist (24 CDP event methods, the two dialog events rebuilt from scratch with empty text; everything else is dropped) and the bridge enables the Page domain itself and denies `Page.disable`. `lib/relay/command-policy.ts` is the deny-by-default argv allowlist `runRelayCommand` checks before any token fetch: elements by snapshot ref (`@eN`) only, no `eval`, no value or text `get`, no `find`, `batch`, `wait --text|--url`, selectors, `tab new`, `keyboard`, `upload` or global flags (refusal: `COMMAND_REFUSED`). `Overlay.*` and `Accessibility.getPartialAXTree` stay out of the agent allowlist (the worker's own scan and highlight use them), and `Overlay.*` events stay dropped. A test pins agent-browser 0.33.2: upgrading it needs a re-review of that allowlist. Review-time worker reads (plan 4c-4, no content script, no server change; each re-applies the typing path's checks: run live and not stopped or held, tab and frame in scope, per-tab lock with screenshots waited out, bounded steps, `needsRegistration` refuses, and a read-only isolated-world evaluation in `relay-focus`): `showUnfilledField(runId)` runs one scan (`SCAN_UNFILLED`: visible, enabled controls that fail `validity.valueMissing` or have `aria-required` and no value; more than 12 candidates sets `capped`, 20k-node cap) and answers only `{ok, found, remaining, sensitive?, capped?}`, never a label, name or value; only the highlighted field is classified (a classification failure counts as sensitive). The highlight is `DOM.scrollIntoViewIfNeeded` plus `Overlay.highlightNode` for about 6 s, cleared on timer, navigation, detach and stop; when Overlay fails or the worker attached itself it scrolls and focuses the field instead. Refusals are fixed strings including `registration pending` and `scan failed`. `armSubmitWatch {runId, reset?}` / `disarmSubmitWatch` and `RunStatus.armed` / `submitted`: the watch reads raw debugger events and reports `submitted` when a main-frame `Page.frameRequestedNavigation` with reason `formSubmissionGet` or `formSubmissionPost` is followed within 30 s by an in-scope main-frame `Page.frameNavigated`; `reset` clears a seen `submitted` without detaching; arming is single-flight. It uses the agent's attach when held, else attaches itself as `reviewAttached`, which never sets the agent-facing `attached` and is let go on disarm or stop. It cannot see XHR or single-page-app submits. The confirmation read (`CONFIRMATION_READ`, after `submitted`, up to 3 tries and 12 s overall, before the run is stopped because stop clears the redactor): only a labelled pattern from a fixed list (`confirmation number|#|code` is kind `confirmation`; `reference|application|tracking number` is kind `other`; `case number` is excluded as a sensitive label) followed by a 4 to 32 character token with a digit. It drops the token on a sensitive shape, 9 or more digits however separated, a date, a known or registered value (substrings too), an email, near-SSN text, or a label outside the list. The token goes only to the panel through `getRunStatus` (React text), never to the server, relay, agent, recents, storage or a log. Records: on relay runs the server builds the opening message from the stored participant, so the unstripped record never transits the browser, and `lib/data/sensitive-record.ts` strips sensitive fields from participant JSON in the `eve-chat` relay route before the message reaches Eve (`calworks_id` included), refuses messages over 256 KB (`message_too_large`, 400) and turns whose prose pairs a sensitive label with a value (`sensitive_value_in_message`, 400); the prose guard is best-effort against accidental pastes, not an adversarial boundary, and it also covers free-text answers to `ask_question` (checked with the question's prompt in front). Traces: `lib/observability/scrubbing-exporter.ts` keeps only allowlisted span attributes when `RELAY_RUNS_ENABLED=1`; it is process-wide (every Eve span, web chats included), Terraform does not set the flag so scrubbing is off until it is set, and the Eve process now ignores `OTEL_EXPORTER_OTLP_*` endpoint variables. Typing a sensitive value (plan 4c-3): the worker message `typeSensitive(runId, value)` types a value the caseworker gave the panel into the field they focused in the tab; the agent is told only `provided` and the value is scrubbed from what the agent sees, except the residuals listed in `docs/browser-extension-todo.md` (values under 3 characters, a worker restart, a page `beforeinput` redirect, Jev-only verdicts). The caseworker focuses the field (the agent's label is not used as a locator). Order: the value is registered for scrubbing first (a refusal there types nothing), then the focused element is checked (enabled, editable text field, in a frame in scope, `masksFilledField` true), then one `Runtime.callFunctionOn` types into that checked element in the isolated `relay-focus` world, never retried, one call at a time (a second concurrent call is refused as `type failed`). It re-applies the agent path's checks (run live, attached and not held, tab in scope and unchanged, screenshots waited out, shared tab hold, 3 s timeout) and never throws or logs. Replies are `{ ok: true }` or one fixed string: `no active run`, `wrong run`, `not attached`, `run is held`, `value not accepted`, `no focused field`, `field not sensitive`, `field out of scope`, `type failed`; the panel maps each to fixed copy (`TYPE_SENSITIVE_COPY`) and never shows the worker's text. Limits: 32 registered values per run, 512 characters (a blank value is refused); a value under 3 characters is typed but not scrubbed (`MIN_KNOWN_LENGTH`). A refusal after registering leaves the value registered. A token refresh with the same run id carries the registered values to the new run (the list is snapshotted after the last await and capped at 256); a worker restart still loses them, and values typed before it are not scrubbed. Residuals: key-driven input masks get no key events, and a page `beforeinput` handler can move focus so the text lands elsewhere (the value is still scrubbed when it has 3+ characters). Accepted residuals and rulings are in `docs/browser-extension-todo.md`.

**Database** — `lib/db/schema.ts` (Drizzle, Postgres). Use the current tables `Message_v2` (`message`) and `vote`, not the deprecated `Message` (`messageDeprecated`) / `voteDeprecated`. `EveRun` (`eveRun`) holds per-(user, chat) Eve run state: session id, continuation token, stream cursor, relay origin, pending questions, progress, `turnIdle` (set when a relay turn reaches `session.waiting`, cleared when one starts; migration 0011, best-effort writes; feeds the state route's `phase`) and `endedAt` (set by Stop, migration 0010); access it through `lib/ai/eve/run-store.ts`, never directly. Queries are centralized in `lib/db/queries.ts`; migrations in `lib/db/migrations/` (Biome-ignored — don't hand-edit). Config in `drizzle.config.ts`.

**Side panel (extension)** — `extension/panel/` (React + Tailwind, built by `pnpm extension:build` into `panel.html`, `panel.js`, `panel.css` beside the worker; tokens are extracted from `app/globals.css` at build time; `APP_ORIGIN` is baked in). It may import only React, radix, cva, clsx, tailwind-merge, lucide, leaf files from `components/ui` (`@/lib/utils` is aliased to `extension/panel/lib/cn.ts`), pure `lib/relay/*` and `lib/data` modules and `extension/src/*`; `tests/relay/panel-bundle.test.ts` fails on `next/`, `server-only`, `@/lib/db`, drizzle, `@typesafe-ai` or `ai` in the bundle graph. The toolbar icon opens it (`extension/src/panel-behavior.ts`). Screens: Home with recents, participant search (system record or entered details), Ready (site and model select), Starting, Running (sections, counts, current step and a session-local action log of at most 200 entries, never stored; a panel opened mid-run shows only what it has seen), Needs You, Allow this site, Review, Confirmed, a fixed error-copy table (`lib/copy.ts`), signed-out. Recents (`lib/recents.ts`) keep exactly `runId`, `siteName`, `startedAt`, `endedReason` for 24 h, max 10, in `chrome.storage.local`; no participant data is stored. The starter writes the recent before the first-turn POST (an id only), and marks it `start-failed` (hidden on Home) when the start leaves no run; the open-time orphan sweep (`lib/orphan-sweep.ts`) stops, once per open, every recent with no end reason that the worker does not hold, then marks it `swept`. It skips recents younger than 90 s, the whole sweep while the worker is unreadable or `restarting`, and the run the worker holds (re-read before each stop); a 404 is final only after 5 minutes; at most 10 stop calls. Every recents write (`addRecent`, `markRecentEnded`, and `loadRecents`' write-back of a cleaned list, which re-reads first) runs under the `recentRuns` Web Lock (`navigator.locks`, shared by every extension page) plus an in-window chain; the sweep loop itself is not locked. Saved details (`lib/saved-details.ts`) keep the fixed 12 non-sensitive fields for 8 h, refuse (not strip) any other or sensitive key, are dropped on read when expired and by a `saved-details-sweep` alarm owned by the service worker. Starting a run (`lib/run-starter.ts`): tab check, the recent (written before the POST), `POST eve-chat` first turn read to its first chunk (15 s), extension token, worker `startRun`, `registrationComplete(runId, 0)`; a failure ends the server run and stops the worker run by run id. The run session (`lib/run-session.ts`) polls the worker (2 s) and the server (3 s; the state route's `phase` is `working`, `needs_you`, `review` or `ended`, and a failed poll keeps the last phase), refreshes the token at 5 min left, ends a run the worker lost only after 7 s of continuous inactivity (a worker status of `restarting`, during a same-run refresh or a service-worker resume, holds that clock for at most 30 s), and Stop calls the server then the worker; reopening mid-run rebuilds from the worker and server using the token's real expiry (`exp`, Unix seconds, from `getRunStatus`; a 5-minute estimate only when the worker reports none), so it does not refresh at once. A same-run refresh carries the known values and the allowed origins (never across a different run id or a worker restart) and accepts a tab on the token origin or a carried one. Worker `stopRun` takes an optional `runId`; `getRunStatus` also returns `tabId`, `exp` and `restarting`. Nothing is logged. Recents store only the run id, site name, start time and end reason. Saved details, when the caseworker ticks 'save', store the fixed non-sensitive fields (name, date of birth, phone, email, address) for 8 hours in `chrome.storage.local`, unencrypted, and never sensitive fields. Needs You cards come from the state route's `pending`; answers go to `eve-chat` as `inputResponses` (`answer-client.ts`) and server refusals map to fixed copy (`unknown_request`, `answers_pending`, `missing_answer`: already answered; `sensitive_value_in_message`; `message_too_large`; `run_ended`). A question with exactly the options `provided` and `skip` and no free text is sensitive: the card offers only those two options and never takes typed text; a free-text question whose prompt `isSensitiveField` flags gets the same typing card, answered with the text `provided` or `skip`. Questions with options stay answerable. The sensitive card's masked input (`screens/sensitive-fill.tsx`, state in `lib/sensitive-fill.ts`) tells the caseworker to click the field in the page, then calls `worker.typeSensitive` (`lib/worker-api.ts`) and answers `provided` on success. `typeSensitive` attaches the debugger on demand when it is not attached, with the relay `attach` scope checks; that typing-only attach never sets the agent-facing `attached`, so the Eve tool still sees `not attached` and rotates its stale daemon. Attach and let-go run one at a time per run in a queue, each step bounded (3 s for typing, 10 s for the agent's attach); the infobar can reappear while the caseworker types. Value hygiene: the typed value lives only in that card's controller while it is mounted and is cleared on success and on dispose; it is never in the panel reducer, a draft, an answer payload, storage, a log or an error string, and a refusal keeps it so the caseworker can refocus and retry. The Allow this site card appears during a worker origin hold, shows the new origin and the tab's URL as origin plus path (no query or fragment), is never auto-approved, and its countdown is informational only (the worker decides; a refusal or the card unmounting ends it); an allowed origin survives a same-run token refresh. Review ('Ready for your review', phase `review`) says the agent's turn ended with no pending question and has a 'Show me the unfilled field' button (`showUnfilledField`, below) with fixed status copy (no promise of a visible box: the fallback is scroll and focus only; a sensitive field may be highlighted and the copy says so). Submit detection: on entering Review the panel calls `armSubmitWatch {runId, reset: true}`; while the worker reports `armed` false it re-arms (one call in flight, no reset), and it stops re-arming before sending `disarmSubmitWatch`; a reopen or review-working-review round trip re-arms with reset, so a detection seen while the panel was closed is lost on purpose. A detected submission never stops the run by itself (a multi-step 'Next' looks the same): when `submitted` arrives the panel asks 'Did you submit the form?' at once, filling in the number when `getRunStatus` carries one ('Confirmation number' for kind `confirmation`, 'Number shown on the page' for kind `other`; 'Looking for a confirmation number...' for up to 12 s, `CONFIRMATION_LOOK_MS`, the worker's read window, while none has arrived). 'Yes, I did' or 'I submitted it' stops the run (server then worker, once) and carries the number shown to Confirmed; No re-arms with reset. Confirmed says 'You confirmed the form was submitted on {site}.' and shows the number as text, labelled by kind. 'I submitted it' stays as a manual press that stops the run and shows Confirmed. Reopening rebuilds the phase card, hold prompt or Review from the worker and server. Limits and follow-ups are in `docs/browser-extension-todo.md`; running the extension against a local app, Eve and relay is in `docs/local-extension.md` (`scripts/dev-relay.sh` starts the relay). Chrome policy and the debugger bar: the panel notice is for a refused attach only. The worker sets `RunStatus.policyRestricted` (`getRunStatus`, `worker-api.ts`) in the `attachTab` catch when Chrome's error says the extension is restricted, and the next successful attach clears it; the Running screen then shows the fixed Chrome-policy copy (`POLICY_RESTRICTED_COPY`, `lib/copy.ts`). A refused CDP command or screenshot only swaps the agent's text for the fixed `POLICY_AGENT_MESSAGE` (the skill tells the agent to end its turn): no flag, no panel notice. The reply string `restricted by policy` is returned only by the panel-facing `typeSensitive`, `showUnfilledField` and `armSubmitWatch` refusals, which the panel maps to the same copy. The Ready screen also says Chrome may show a debugging bar while the agent works (`DEBUGGER_BAR_COPY`). A policy error inside attach's inner `Page.enable` or `getFrameTree` falls into the generic error, and nothing has been exercised on a managed Chrome.

**Artifacts** — interactive side-panel artifacts in `artifacts/` with shared logic in `lib/artifacts/`: `browser` (live Kernel session viewer — `client.tsx`, `client-kernel.tsx`, `server.ts`), `code`, `image`, `sheet`, `text`. The `artifacts/session_*` directories are runtime scratch output, not source.

**Prompts** — legacy route: `lib/ai/prompts/` (`web-automation.ts`, `browser-and-forms.ts`, `application-protocol.ts`) compose the system prompt; markdown references the model can read on demand are in `lib/ai/prompts/references/`. Eve agent: `agent/instructions.md` (always-on) plus `agent/skills/*` (loaded on demand) carry the equivalent content — see `agent/README.md`'s section-by-section mapping if reconciling the two, but not its overall "demonstrative" framing (stale, see above).

**Jev (TypeSafe System One)** — `lib/jev/` wraps the `@typesafe-ai/sdk` client for small, fast, typed judgments (choice / noul / score with calibrated probabilities) where code needs semantic understanding. The design rule: **questions are written in code** (`lib/jev/questions.ts`) and called from code, never composed by the model at runtime — fixed questions can be versioned and regression-scored. `lib/jev/client.ts` is deliberately free of `server-only` so the Eve runtime could import it. `askJev` never throws: any failure (no key, rate limit, timeout, abort) returns `{ ok: false }` and the caller falls back to its pre-Jev behavior, so nothing blocks a form run on TypeSafe being reachable.

A fourth, runtime call site is `app/(chat)/api/relay/classify-field/route.ts` (the `sensitive-field` feature, called from the extension worker in plan 4b). It answers one verdict per field: `true` for anything `isSensitiveField` flags (no Jev call), `true`/`false` when Jev answered with a finite noul (`true` at or above `NOUL_THRESHOLD`), and `null` (no verdict) when the feature is off, `askJev` fails or throws, the answer is malformed, or the sanitized descriptor is empty. It never turns a failure into a boolean because the worker caches every boolean for the run; on `null` the worker keeps the deterministic verdict. The caller ORs the Jev verdict with the deterministic classifier so Jev can only escalate masking. (`sensitiveFieldIsSensitive` in `lib/jev/questions.ts`, which fails toward sensitive, is not used by this route.) The three call sites below are all **annotate-only** — they add a `jev` field to rows the agent already produced and never drop or rewrite one (dropping a row from a benefits application needs a threshold chosen from observed data, which does not exist yet): `gapAnalysis` rows get "does the record already answer this?", `formSummary` rows get "is this value grounded, and is the agent's own `source` label accurate?", and `resolveFieldValue` picks a verbatim value from record-derived candidates. Gated by `JEV_FEATURES` (comma-separated, or `all`; empty disables everything) — a server-side env var, **not** `lib/feature-flags.ts`, because that resolves overrides from `localStorage` and yields only `defaultValue` on the server. The participant record reaches these tools via `lib/jev/participant.ts`, which parses it back out of the caseworker's opening message (there is no other carrier). An earlier generic "ask Jev anything" tool was removed: letting the model author its own questions defeats the point, since such questions cannot be versioned or regression-scored.

**Both agent trees are wired**, sharing everything under `lib/jev/`. Eve needs one extra hop because its tools are module-level `defineTool` default exports with no construction step, and `ToolContext` exposes no message history — so the record cannot be passed in or looked up. Instead `agent/hooks/participant.ts` lifts it out of `message.received` into a `defineState` slot (`agent/lib/participant-state.ts`), and `agent/lib/jev.ts` reads it back. A subagent inherits no state, so `agent/subagents/form_review/tools/form_summary.ts` degrades to un-annotated rows rather than erroring. Eve counterparts: `agent/tools/gap_analysis.ts`, `agent/tools/form_summary.ts`, `agent/tools/resolve_field_value.ts`. `JEV_FEATURES` and `TYPESAFE_API_KEY` reach Eve without extra wiring: `scripts/start-container.sh` starts it as a plain child process, which inherits the container env.

`lib/jev/telemetry.ts` traces every call: one `jev <feature> batch` span per card tool (carrying
`rows_attempted` vs `rows_annotated`, and `enabled: false` when the flag is off) with one
`jev <feature>` child per request. Both exporters run `filterAISpans: true`, so the tracer scope
`labs-asp.jev` has to stay in the `KEEP_SCOPES` set in **both** `instrumentation.ts` and
`agent/instrumentation.ts` or the spans are silently dropped in that process. The same module
prints a JSON line per batch to stdout, which is the only signal where no exporter is configured.

Braintrust also supports Jev as an online-eval judge — see `evals/README.md`.

**Feature flags** — `lib/feature-flags.ts`. Env-aware defaults, overridable per-browser via `localStorage` (`ff:` prefix) through a dev-only menu. Current flags: `declutterToolCalls` (show only value-bearing tool calls in prod) and `useEveAgent` (route chat through the Eve adapter route instead of the legacy loop; defaults `false`).

**Deployment** — Cloud Run, not Vercel (an earlier Vercel migration was explored and abandoned once a working Cloud Run deployment already existed). `scripts/start-container.sh` is the container entrypoint: it applies DB migrations, conditionally bootstraps the Eve workflow Postgres schema (`scripts/bootstrap-workflow-db.ts`, only when `WORKFLOW_POSTGRES_URL` is set), then starts the Eve runtime (`.output/server/index.mjs`, built by `eve build`) and `next start` as sibling processes, supervising both — either one dying takes the container down so Cloud Run replaces the instance. `terraform/cloud_run.tf` sets `WORKFLOW_POSTGRES_URL` against the same Cloud SQL instance the app already uses, because Eve's default local-file workflow world doesn't survive this service's routine instance churn (`min_instance_count = 2`, best-effort session affinity). Pilot rollout settings (all default to today's behavior; `terraform/variables.tf`): `relay_min_instances` (0 or 1), `relay_runs_enabled` and `relay_token_endpoint_enabled` (set `RELAY_RUNS_ENABLED=1` and `RELAY_TOKEN_ENDPOINT_ENABLED=1` on the app, only where the relay is deployed), `relay_extension_origin`, `relay_allowed_models`, `relay_allowed_hosts` (exact hosts, replacing the `.run.app` suffix in two applies because a wrong host answers 421), `relay_allowed_host_suffixes` (default `.run.app`) and `relay_command_duration_metric_enabled` (log-based distribution metric; needs `logging.logMetrics.create` on the deploy identity). `terraform/relay.tf` checks the app's `eve-internal-secret-<env>` at plan time and refuses an empty host list or a `relay_extension_origin` that differs from `extension/EXTENSION_ID`. `deploy.yml` builds and deploys the relay only for dev and prod when the repository variable `RELAY_ENABLED` is `true` (previews never get one; the variable must be repository-level, and setting it turns on both the dev and prod relays, so the prod secrets must exist first); `promote.yml` fails, rather than warns, when the relay is enabled and the promoted SHA has no relay image, so promote only SHAs deployed with the relay on. Neither workflow passes the new variables yet: wire both (`-var=` in deploy, `TF_VAR_` in promote) before setting one. Release packaging: `scripts/package-extension.ts` (helpers in `scripts/package-extension-lib.ts`) runs the release build (`EXTENSION_RELEASE=1`) and writes `extension.zip`, optionally `updates.xml` (`--update-url`, `--package-url`) and, locally only, a CRX3 signed with the unencrypted PEM named by `EXTENSION_PEM_PATH` (kept outside the repo); `.github/workflows/extension-release.yml` (manual) builds the zip as an artifact for inspection and never signs. The manifest sets `minimum_chrome_version` 120. Policy templates are in `deploy/chrome-policy/`, and `docs/rollout-pilot.md` is the runbook.

**Evals & observability** — `evals/*.eval.ts` is a Braintrust eval suite (run via `pnpm eval*`, see Commands) covering tool selection, navigation, gap-analysis, hallucination, verbosity, and other scenario/regression checks against the web-automation agent; `evals/online/` applies scoring rules to live production traces rather than a fixed dataset. Traces reach Braintrust via OpenTelemetry: the root `instrumentation.ts` covers the Next process, and `agent/instrumentation.ts` separately exports Eve's agent spans — required because the Eve agent runs in its own server process, which the root instrumentation file never sees. Both use `@braintrust/otel` + `@vercel/otel`. `lib/observability/browser-telemetry.ts` is the shared span-collector interface `lib/kernel/telemetry.ts` implements.

**Errors** — throw `ChatSDKError` (`lib/errors.ts`) for API/route errors rather than raw `Error`s.

## Conventions

**React/frontend (`.cursor/rules/react.mdc`):**
- Tailwind classes only for styling — no inline styles, no separate CSS. Add a Tailwind variable if a new style property is needed.
- Event handlers use a `handle` prefix (`handleClick`, `handleKeyDown`); prefer typed `const` arrow functions over `function`.
- Use early returns; include accessibility attributes (`aria-label`, `tabIndex`, keyboard handlers).

**Testing:** Default to `vitest --browser` (Playwright + `vitest-browser-react`); only write node/jsdom tests if explicitly asked. Import components under test from source; import test helpers from `vitest-browser-react`. Prefer `getByRole`/`findByRole` (name with regex) over `getByTestId`. Use `findBy*`/`waitFor` for async (no `setTimeout` polling), MSW for HTTP, and local `vi.mock` for module mocks. Test layout: `tests/client/` (component tests, browser-mode by default — but a file named `*.node.test.ts` inside `tests/client/` runs in `pnpm test`'s separate `node` project instead, for anything that can't resolve in a browser bundle, e.g. `browser-telemetry.node.test.ts`, `kernel-telemetry.node.test.ts`); `tests/agent/` (a fully separate node-mode suite for Eve/tool-adjacent tests, NOT part of `pnpm test` at all — run via `vitest.config.node.mjs`, see Commands); `tests/e2e/` + `tests/routes/` + `tests/pages/` (Playwright).

**Documentation:** Write for engineers — avoid marketing language ("powerful", "out-of-the-box", "production-ready", "makes it easy", "Check out"). H1 headings use Title Case.
